# Policy Index and Precedence

The files in `policies/` are the development policies for this project. They work together as one governance system and apply to every AI agent and every human contributor, whatever tool they use. Apply the policies that are materially triggered by the task; do not dump every checklist into every response.

`AGENTS.md` lists every policy and when it applies. Tool-specific files (`.cursor/rules/`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`) only deliver these policies to a particular tool. If a tool-specific file and a file in `policies/` disagree, `policies/` wins.

## Policy Precedence

When guidance appears to conflict, resolve it in this order:

1. Explicit user instruction, unless it would break a non-negotiable data-safety rule in `policies/privacy-redaction-and-synthetic-data.md` or `policies/security-compliance.md`.
2. Spec Kit constitution at `.specify/memory/constitution.md`, once it exists.
3. Security, privacy, compliance, and evidence-integrity policies.
4. No-stubs, testing quality, and human-review policies.
5. Ontology, data-contract, persistence, and provenance policies.
6. Architecture, four-surface, MCP, and cross-platform policies.
7. Testing program, release, dependency, observability, model, performance, documentation, and visible-surface policies.
8. Repository-local context in `policies/project-context.md` and anything generated by Spec Kit.

If a conflict remains, stop and ask the user rather than silently choosing the easier path. A user can always choose a stricter option; an agent must never choose a weaker one on the user's behalf.

## Policy Types

- Core policies are always active: this index, student mode, project context, security, privacy and test data, no stubs, Spec Kit workflow, and human review.
- Conditional policies apply when their subject area is materially touched, such as models, MCP, persistence, dependencies, performance, documentation, user-facing copy, or release automation.
- Repository-local context (`policies/project-context.md`) describes the stack, commands, paths, and local conventions for this project once intake and planning have identified them.

## Shared Data Taxonomy

Use consistent language across policies, specs, docs, and agent summaries:

- Source evidence: original media, forensic images, mounted evidence, or operator-selected source records. Must remain read-only.
- Derived artifacts: extracted files, sampled frames, thumbnails, OCR/transcripts, model outputs, reports, exports, caches, and temporary working data.
- Investigative metadata: case labels, review status, hash lookup results, tags, notes, job metadata, and triage context.
- Protected identifiers: victim/person identifiers, agency case numbers, investigator identities, sensitive evidence paths, credentials, API keys, and non-public operational details.
- Provenance and audit data: who/what/when/action/result, tool/model versions, parameters, hashes, source references, and validation status.
- Public or synthetic data (Tier T0/T1): benign or realistic-synthetic fixtures safe for committed and shared channels.
- Controlled test/demo data (Tier T2/T3): agency-approved or operational samples allowed only in documented, approved local or production environments, never in this course, and never mislabeled as T0 in records. See `docs/test-data-handling.md`.

## Agent Output Discipline

Final responses should summarize only the policy impacts that were materially triggered. For Spec Kit-driven work, use the Spec Kit output summary as the umbrella and include specialized checklist items only for affected areas. Write summaries in plain language the user can act on.
